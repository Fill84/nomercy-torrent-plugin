# The user interface

## Two rules

**Every number is real.** A count that is not known is not drawn as nought; it says what is missing.
0.3.4 showed "0 downloads" while two were running.

**Everything updates live.** No page polls. The pipeline publishes to the activity journal, the
journal pushes a snapshot over `IPluginHubContext.PushAsync("torrent-downloader:changed", …)` at most
once every 250 ms, and every page renders from that snapshot.

## Overview — the landing page at `/`

The owner's requirements of 15 September 2026, `docs/specs/show-list.md`. The page opens with the
run's status line (Run and Stop), then a block per tv and anime library, one library at a time under
a tab each (§ Tabs): its preferences on one line
with an **Edit** button, and a table of every show in it — show, year, missing, quality, codec, tags,
state. A row's state is **On** or **Off** — a show switched on follows its library until the owner sets
something on the show itself — and every row carries two buttons:
**Switch on**/**Switch off** and **Settings**. The contract has no toggle or tag field inside a table
row, which is why the switch is a button. A table shows 50 rows, switched-on shows first and each
group alphabetical; **Previous** and **Next** go to `/libraries/:id/shows/:page`, a page number in
the path because the web app sends the plugin a page's path and drops anything after a question
mark. The same address is the library's tab: `/libraries/:id/shows/1` draws the overview with that
library chosen, and `/` draws the first.

## Tabs — a page with two or more tables

GitHub issue #4, 13 October 2026: the Queue, the Activity page during a run and the overview stacked
their tables below each other. Since 15 October 2026 a page with two or more tables shows one at a
time, under a row of tabs, one per table; a page with one table has none.

| Page | Tabs | Addresses |
| --- | --- | --- |
| Overview | one per library, the library's name and how many shows are listed (under a search, how many match) | `/` (the first), `/libraries/:id/shows/:page` |
| Activity, while a run is going | Stages, Now (in flight), Notes (noted) — the stages carry no count, being the same six rows on every run | `/activity` (the first), `/activity/:tab` with `stages`, `now`, `notes` |
| Queue | Looking (being looked for), Waiting to air | `/queue` (the first), `/queue/:tab` with `looking`, `waiting` |

**The tab is in the path, never the query.** The web app forwards a page's path and nothing after a
question mark, so a tab in a query would be lost on every reload. A path naming no tab, or one the page
does not have — the stages of a run that has ended — draws the first. Each tab address is declared in
`Pages.Routes` and answered at the address the web app fetches before drawing it, and the plugin's own
navigation marks the page a tab belongs to.

**Tabs are buttons in a row, as the navigation is.** The contract has no tab component (media-server
#593). A `PluginRow` of `PluginButton`s that navigate is what both clients already move along: focusable
on a television, with left and right stepping between them. The chosen tab is `primary` and the others
`ghost`, exactly as the navigation marks the page being read, and a count is drawn only where it is
known (§ Two rules). Downloads, History, Sources and Settings have one table or none, and no tabs.

## Sort, filter and paging — every table

GitHub issue #5, 13 October 2026; the platform side is media-server #593, open, which asks the SDK for
a sortable flag per column and a paging block per table. Until the contract has those fields no client
offers a sort or a search box, but since 15 October 2026 every table answers the keys #593 names when
they arrive in the view request's query (`PluginViewRequest.Query`): `sort`, `order`, `filter`, `page`
and `pageSize`. They name no table, because a page draws one table at a time (§ Tabs).
`Views/TableRows` does it for every table the same way: filter on the words the cells show, then sort,
then page.

| Table | Sorts by value | Default order | Pages |
| --- | --- | --- | --- |
| Overview, a library's shows | year, missing, quality (the rest by their words) | switched on first, then title | yes, 50; `page` in the query wins over the path's |
| Activity: Stages | — (stage and counts by their words) | the run's order | no |
| Activity: Now | stage, by its place in a run | as the journal holds them | no |
| Activity: Notes | time, step by its place in a run | oldest first | no |
| Queue: Looking | episode (show, then season and number), attempts, last tried | the order a search asks | no |
| Queue: Waiting to air | episode, air date | by air date, undated last | no |
| Downloads | progress (fraction done), rate (bytes down), seeds, peers, ratio, left | the open grabs as stored | no |
| History | when, why (a line with no reason last) | newest first | no |
| Sources | last asked, rows, took, askable again | the catalogue's order | no |

**The shown text is what a filter matches**, because every cell here is text: each page writes its
own sizes, rates and times, since the client's `Bytes`, `Rate` and `Duration` cells cannot say "not
known" (§ Two rules). A button's label is not text a filter matches. **The value is what a sort uses**
where the words would mislead — "10% of 1 GB" is before "9% of 1 GB" as text, "1.5 s" before
"900 ms" — and a value not known sorts last in either order. An unknown key or order is the table's own
order; a page past the end is the last. `pageSize` is honoured from 1 to the table's own 50 and is the
50 otherwise (decided 15 October 2026 for `S14-07`, so no client can have the plugin draw a library of
thousands at once). Under any key the overview's paging line adds how many shows match:
"page 2 of 3 · 120 shows", and Previous and Next are not drawn: they go to the page in the path, fifty to a page with no query, so under ten to a
page the Next of page 2 drew shows 101 to 150 and dropped the sort and filter. A client paging by query
pages by query. A tab's count stays its table's total under a filter. Keys are read whatever their case
(`?Sort=` is `sort`), since ASP.NET reads a query that way and the server hands the keys on as sent.
With no key every page is exactly as it was. The plugin's own prefetch
address (`PagesController`) passes the query on, as the server's view endpoint does.

The web app forwards no query today (`PluginScreen.vue` sends `route`, `surface` and `input`), so
until #593's client side lands these keys reach the plugin only from a client that sends them itself.

## Long text — no table scrolls sideways

15 October 2026, on beast-unit: the Sources table scrolled sideways, because Torrentz2's Refusal cell
held its whole refusal — "torrentz2.nz did not answer: No such host is known. (torrentz2.nz:443)
(https://torrentz2.nz/search?q=Dark Matter S02E08) It is left out of the rest of this run". The web
app draws every cell on one line (`whitespace-nowrap` in `PluginTable.vue`) and gives each column at
least the width of its longest cell (`minmax(max-content, …)`), so a single long cell widens the whole
table past the page. A line of text (`PluginText`, a paragraph) wraps. The fix is the plugin's
(`../nomercy-app-web` is not changed for the plugin's pages).

**The measure.** The owner's screenshot had the table about 1600 px wide. A cell is Inter at 16 px,
about 9 px a character in ordinary words, padded 12 px each side: n characters take about 9n + 24 px,
headings included. Every cap below is what a table's other columns leave at their widest real content
(`Views/LongCells`). The longest episode release name in the captures is 81 characters
(`Lucky.S01E04.Too.Close.to.See.It.2160p.ATVP.WEB-DL.ITA.ENG.DD5.1.DV.HDR.H.265-G66`, TorrentGalaxy).

| Table | Long column, most characters, how it is cut |
| --- | --- |
| Overview, a library's shows | Show, 48, at a word; Tags, 48, at a word |
| Sources | Refusal, 77, first sentence |
| History | Which, 60, at a word (a release); Why, 77, first sentence |
| Activity: Notes | What, 77, first sentence |
| Activity: Now | Episode, 83, at a word ("release · source"); Waiting on, 77, at a word (the release grabbed) |
| Downloads | Release, 16, at a word; State, 34, first sentence |

**First sentence** (a refusal, a reason, a note, a state): the text up to the first web address, then up
to its first full stop, cut after the last whole word that fits. **At a word** (a release name, a title,
a tag list): cut after the last space, dash, underscore or dot that fits, never at a full stop, since
"Atmos. X265" in a name (The Pirate Bay) ends nothing, and never at a dot before a digit, since "H.265"
and "DD5.1" are one word each. A text with nowhere to cut, such as an info hash standing for a torrent
added by hand, is cut where the cell ends. A text that fits and holds no web address is the cell as it
is. **A web address (http or https) is never in the cell**: it is what ran Torrentz2's refusal off the
page, and an address with a space in its query does not end where it looks to. A host and port such as
"(torrentz2.nz:443)" is not a web address and stays.

The whole text of every cell drawn short stands under the table as a line of its own, in the order of
the rows drawn, and on a page with tabs under the chosen tab's table. On the overview the lines stand
between the table and its paging line; on Downloads they stand after the field that takes a magnet, which
stays directly under the table. `Views/TableRows` does it for every table, after the filter, the sort and
the page, so `filter` and `sort` read the whole text and a row is found by a word that is only in its
line under the table. Downloads keeps its State whole for every state the page writes itself ("grabbed,
not started (downloading)" is the longest, at 34). The Download stage on Activity counts downloads by
their state without the client's error, which is on the Downloads page.

**The widest real row of every table, at 1600 px:**

**Downloads has no Destination column** (the owner's decision of 15 October 2026). It was the incomplete

**A show's settings, `/shows/:id`**, is one form with one Save: switched on, quality, codec and
specials — each able to follow the library — and for wishes, musts and forbidden a comma list and a
field for one tag appended on Save. Below it, what applies with the library counted in. **A
library's preferences, `/libraries/:id`**, is the same form without following. A refused form names
the field and saves nothing, not even that the show was saved. A missing count the plugin did not
make says "not counted" rather than nought.

| Section | Answers | Components |
| --- | --- | --- |
| Status bar | is it working, on what, since when | `Container`, `Badge`, `Text`, `Button` |
| Stages | how far along, where it is stuck | `Progress` per stage with counts |
| Now | which episodes are in flight this second and what each is waiting on | `Table` |
| Sources | which sites are healthy, waiting, or broken | `Row` of `Badge`, `Table` on click |
| Downloads | what is transferring, with ratio while seeding | `Table` with `Progress`, `Bytes`, `Rate`, `Duration` |

**Run** starts a full cycle, answers immediately, and stays disabled while that cycle is open —
which is until nothing it started is left in hand and maintenance has run, not merely until the
search is done. A download and an encode a cycle asked for are still that cycle.

**The pages are told only while somebody is looking, and only of a real change.** Every push makes
the web app fetch the whole view again over HTTP, so a running download used to be a page load a
second per open tab, and the same work pushed to nobody on a server with no tab open. The hub cannot
say who is watching; a fetch can. A page being fetched says somebody is looking, a push nothing
fetches after within fifteen seconds says nobody is, and ten minutes with nothing to push lets the
watch rest until the torrent client does something again. The heartbeat that samples the client
exists only while somebody is looking, and it compares each reading with what the page was drawn
with, so a page is never pushed what it already shows.

**Stop** ends the whole run: nothing it had in flight stays on the page, its stage rows and notes
are cleared, and the browser is closed. Transfers already handed to the torrent client keep going —
stopping a search is not stopping a download. The next Run starts again from the top of the queue.

While a run is going the status bar says since when, as a clock time. When nothing is running it
says when the last run ended and how — finished, stopped or failed, kept across a restart — and when
the next is due, worked out from the cycle's cadence and when the last cycle finished (NCrontab, in
UTC). `EmptyState` is for a plugin with nothing configured, not for an idle one.

While a run is going the Activity page shows a row per stage with its counts — Warm-up, Names,
Find, Decide, Grab, Download — and, for every episode it has not decided yet, what it did: which
source was asked and what it answered, which name was refused and why, and every question to every
indexer with the rows it came back with. The owner's decision of 11 September 2026: the page
shows literally what the plugin does.

Anything the pipeline does that cannot appear in **Now** is a stage that has not been instrumented,
and an uninstrumented stage does not ship.

## Actions

Every one of these is an endpoint and a control on the page named:

| Action | Page | Does |
| --- | --- | --- |
| `RunNow` | Overview, Activity, Settings | start a full cycle in the background |
| `StopRun` | Overview, Activity | cancel the running cycle; transfers keep going |
| `SwitchShow` | Overview | switch one show on or off, saving nothing else (`shows/:id/on`, `shows/:id/off`) |
| `SaveShowSettings` | Show settings | save one show's form, all of it or none (`shows/:id/settings`) |
| `SaveLibraryPreferences` | Library preferences | save one library's form, all of it or none (`libraries/:id/preferences`) |
| `SearchNow` | Queue | search one episode immediately, outside the cadence |
| `PauseDownload` | Downloads | pause a transfer, keeping its pieces |
| `ResumeDownload` | Downloads | resume a paused transfer |
| `CancelDownload` | Downloads | stop it, remove it, and return the episode to missing |
| `AddTorrent` | Downloads | add a magnet or `.torrent` by hand, outside the search chain |
| `SaveSettings` | Settings | save the settings, with validation |
| `AddIndexer` / `SaveIndexer` / `RemoveIndexer` | Settings | the owner's own indexers |
| `AddPrivateTracker` / `SavePrivateTracker` / `RemovePrivateTracker` | Settings | the owner's own private trackers |

`AddTorrent` still runs the finished file through staging and the encode dispatch, because a torrent
added by hand is an episode like any other. Its episodes are read out of its own file names once it
has finished, and matched against the shows the server offers.

**When it names no show the owner has, the show is added and the pack is taken on next tick.**
That is the one thing that turns it into an ordinary grab: an encode is asked for by the server's own
episode id, and a show with no row has no episodes and no ids.

**It is the server's own call, and the same one *Add content* makes.** The show is looked up with the
server's metadata providers and imported with `DispatchJob<ShowImportJob>(id, libraryId)`. Which
library is decided by what the files read as: numbered by season is television, numbered from the
start of the series is anime, which is the one thing a file name says about it.

**Asked once per run.** The import runs on the server's own queue, so the show is not there the
moment it is dispatched and a tick a minute later still finds it in no library. Nothing else happens
on the tick that asks: the files stay where they are and the grab stays open until the show lands.

**Nothing is ever handed to the encoder unnamed.** A file sent with no media id is put in a
`VideoEncodeJob` whose `Id` is empty, and that job resolves its id against `Movies.Id` or
`Episodes.Id` and nothing else: it finds no row, returns having done no work, and the queue records
it finished. On 31 August 2026 that was nine files, nine jobs finished inside two minutes, and
nothing written to the library.

**Where the show cannot be added** — no library of that kind, no provider that knows it, or a server
without the parts — it is left exactly where the owner put it and the History page says which show
its files name, once.

`AllowRelease` recorded an `allowed` history entry naming the release and the reason it had been
refused, so a page never silently contradicted an earlier decision. Since 15 September 2026 there is
no `AllowRelease`: a refused release name offers no button to download it anyway, and what decides is
the show's settings, changed on its own form (`docs/specs/pages.md`).

**Where each control sits.** A table cell holds a value and not a button, and a row carries one
action, so the layout follows from that rather than from taste. A row *is* the control where there
is one thing to do with it: the Queue's rows search that episode now. Where there are several — Downloads, with pause, resume and cancel — the numbers
stay in the table and a strip of buttons per download sits under it, each naming its release, or an
owner with four downloads cannot tell which Cancel is which. Pause and resume are one button that
says which it is, because a torrent is one or the other. Cancel carries a `PluginConfirmation` and is
marked destructive: it deletes what has been downloaded so far, and leaving that to the client would
have one asking and another not. `AddTorrent` is a `Form` with one field, because a button with
nothing to type into is an action nobody can use.

## Settings

**One form, one Save, for everything on the page.** The owner asked for it on 12 September 2026
after seeing four Save buttons scattered down the page. It costs what the old shape avoided: one
Save is one post, and a single refused field saves none of them — so the refusal names the field and
is drawn at the top of the page. The groups below are the reading order of that one form, not
separate forms.

- **Folders** — incomplete and intake. Validated on save; a folder that cannot be written says so on
  the page. A warning when the two are on different volumes, because every completion then pays a
  full-file copy.
- **No quality, codec, tag or language setting.** Those are set per show and per library on the
  overview (`docs/specs/show-list.md`); a post that still names a `profile.*` field is refused by name.
- **Start a cycle** — one interval: every 15 minutes, every 30 minutes, every hour, every 6 hours,
  every 12 hours, or once a day at 4am, and the values are the cron expressions they stand for.
  **Nothing sooner than 15 minutes apart**, on the list or typed by hand under **Show advanced**
  (`docs/specs/release-names.md`). An expression is held to that from the minutes it fires: no two of
  them in a day, the last and the next day's first included, are closer than 15 minutes. For anything
  sooner there is Run. **No label says a
  change needs a restart**, because the plugin keeps its own clock. See `docs/01-plugin.md` § One
  cycle, driven by events.
- **Torrent client** — downloads at once, maximum download, and the listen port with its state.
  A speed is a list of presets — unlimited, 1, 5, 10, 25 MB/s — with a box beside it in MB/s for
  anything else; the box wins when it is filled in and blank leaves the list's answer alone. Stored
  in bytes a second exactly as before, so nothing downstream changes: the page simply stops asking
  the owner to type 10485760.
- **Private trackers** — host and announce URL, the URL carrying `{passkey}` where the passkey goes.
  The passkey is write-only: the page renders that one is set, never the value, and is handed only
  the names of the secrets that exist so it has no value it could render.
  **Seeding appears here and only here** — seed ratio, seed hours and maximum upload — and only when
  a private tracker exists. Nothing on a public swarm is ever uploaded (`docs/06-torrent-client.md`
  § Uploading), so without one those three decide nothing, and a line says why rather than leaving
  the absence to be noticed.
- **Advanced** — stall minutes, metadata timeout, encryption, the resume interval, the cycle's
  cadence as a raw expression, and the **log level** (Error, Warning, Information, Debug, Trace;
  Information until the owner chooses), with the folder the log file is in written under it — Debug
  and Trace are written there and nowhere else, because the server's log takes nothing below
  Information. GitHub issue #7, 14 October 2026.
- **Run now**.

**Own indexers and the shipped sources are not here.** `S12-08` moved them to the Sources page,
which is the page about sources. See § Sources.

**Show advanced is one switch per page, and it saves nothing.** It is a display state: it decides
what is drawn and nothing about what the plugin does, and a field hidden behind it still applies.
It is a button rather than a field — a field would be posted with its section and written into
`config.json` — so it flips a flag the plugin holds in memory and the page is drawn again from it.
It does not survive a restart, which costs one click and keeps a switch that decides nothing out of
the file that decides everything.

## Sources

What each site last answered, and the two things an owner may change about them.

- **The table** — source, last asked, rows, took, refusal, askable again. A refusal is in the
  words of the site. Nothing here is an address: a shipped source is not the owner's to edit, its
  address and reader are measured against a real capture, and a page that let them be typed over
  would be a page that breaks a reader. A site left out of the rest of a run — no answer, or still
  behind a challenge after the second attempt — says why here (`docs/specs/run.md`).
- **Own indexers** — name, address with `{query}`, kind, priority, minimum interval, API key,
  enabled. The API key is write-only: the page is handed only the names of the secrets that exist,
  so it renders that a key is set and has no value it could leak.
- **A switch per shipped source**, under **Show advanced** — an owner who came to see what answered
  should not have to walk past a switch for every site. Every source is on until it is turned off:
  `DisabledDefaultSources` records what is *off*, so a source nobody has touched is absent from it,
  and one added by a later version is enabled rather than missing from a list written before it
  existed. The switches post `source.<name>` and the applier writes the list.

## Components

- `PluginTableCellType`: `Text`, `Progress`, `Badge`, `Bytes`, `Rate`, `Duration`
- `PluginBadgeVariant`: `Neutral`, `Info`, `Success`, `Warning`, `Danger`
- `PluginActionType`: `PlayMedia`, `Enqueue`, `Navigate`, `CallPlugin`, `OpenWebView`, `RefreshView`
- `PluginLayout`: `Standard`, `ListDetail`, `Grid`, `Form`

**A component's name is not `PluginComponentType`.** That enum maps `Container`, `List`, `Row`,
`Grid`, `Card`, `Detail`, `Form` and `Table` all onto the single string `"NMCard"`, and the client
resolves a node in two steps: a design-system name is drawn as a design-system component, anything
else is looked up in the plugin map. So every node sent as `"NMCard"` was drawn as a plain card and
the plugin component behind that name was never reached — which is how a form became a clickable box
that saved `{}`. Nothing here may send a design-system name, and a test asserts it.

The names below were read off the client — `types/plugins.ts` for the names, each `Plugin*.vue` for
its props. `Views/Ui.cs` is the one place they are written, and it holds only the ones a page draws:

| Sent | Draws |
| --- | --- |
| `PluginText` | a line of text |
| `PluginRow` | things side by side, and a table row |
| `PluginDetail` | a titled panel |
| `PluginButton` | a button |
| `PluginForm` | a real `<form>` that collects its fields and posts them |
| `PluginTable` | a table with columns, and its own empty message |
| `PluginBadge` | a badge |

The client also has `PluginContainer`, `PluginList` and `PluginEmptyState`. **No page draws them**,
so `Ui` does not carry them; a page that needs one reads the client again and adds it with its
caller. `PluginEmptyState` is the one worth knowing about: it is for a plugin with nothing
configured, and this plugin has no such page state — every "nothing here" it shows is a table's own
empty message, because an idle plugin with nothing in flight is working correctly.

**Every page is `Standard`.** The same shell, at the same width, on all of them.

`Form` is a 40rem column and `ListDetail` puts the content in half the width with a pane beside it —
and every page here carries the same bar of eight tabs. A page that asks for a different shell moves
that bar and everything under it, so the content jumps on every visit and jumps back on the way out.

This was settled on 11 August 2026 and undone on the 14th, when Shows and Queue were given
`ListDetail` and Settings its `Form` back. The Shows page then shipped as a squeezed half-width
column with its last column cut off and a dead pane beside it. `EveryPageIsTheSameShellTests` holds
the pages against each other now, because each one was only ever checked against itself. Since
15 September 2026 there is no separate Shows page: the overview lists the shows
(`docs/specs/pages.md`).

Two mounts in `plugin.json`, matching `IUiPlugin.NavEntries` exactly (a test asserts it):

- `dashboard` → `/`
- `settings` → `/settings`, which the web app shows in the user menu

Not under `library`: the owner's decision of 11 September 2026, the plugin belongs in the dashboard
and the user menu and nowhere else.
