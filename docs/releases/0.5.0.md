## NoMercy Torrent Downloader — v0.5.0

The version where the plugin works the way it was always meant to, in two halves.

**Searching:** the scene databases are asked what an episode was released as. That exact name is put to every indexer letter for letter. Everything with the same info hash becomes one torrent, carrying every tracker the indexers knew.

**Everything after:** one cycle runs from the feed to maintenance, each step started by the one before finishing. Nothing in it polls.

Everything below was measured on a real server, not read.

### One cycle, driven by events

A cycle is feed → search → download → staged → encode → maintenance. It is not four cadences ticking beside each other any more.

- **Three things start a cycle:**
  - the Run button;
  - the server finishing a library scan;
  - your own interval, hourly by default.
- **A trigger during a cycle is added to it.** The cycle's feed and search run again without taking anything it already took. Nothing is started beside it and nothing is dropped.
- **A finished download is staged the moment its last piece verifies.** The encode is asked for straight after. A download that finished while the server was down is staged when the server says the plugin has loaded.
- **An encode is heard, not asked about.** The server's own encoding events close a grab the moment the encode ends. The plugin used to ask the server about every job of every grab once a minute.
- **The library decides when an encode has arrived.** The server says nothing about a job taken out of its queue by hand, or one that ends with nothing to encode. A grab waiting on such a job is closed by the first pass that finds its episode in the library, or when you cancel it on the Downloads page. No clock gives up on it any more. Six hours of silence used to fail the grab and download the episode a second time.
- **An encode is never asked for twice.** A restart used to ask again for every grab that was waiting, and put a second job in a queue that had kept the first.
- **Maintenance runs when nothing is left in hand**, and only then. That means nothing the client holds, nothing staged, and nothing waiting on an encode. It used to run at four in the morning whatever was downloading. Run stays disabled until that point.
- **A cycle starts at most once an hour.** That holds on the list and for an expression typed under Show advanced. Every cycle searches every indexer; for anything sooner there is Run.
- **A saved interval takes effect at once.** The plugin keeps its own clock, set to the moment the next cycle is due. A server reads a plugin's schedule only when it loads it, so a changed cadence used to wait for a restart.

### The torrent client keeps its own house

Expiring magnets, noticing stalls, enforcing the download limit and writing resume files all used to happen inside the call that draws the Downloads table. Something therefore had to draw it every minute. Each now happens when its own moment comes.

Three things cannot be told by an event, because they are about something *not* happening:
- a magnet nobody serves;
- a download with no byte for twenty minutes;
- seeding hours running out.

Each torrent holds one timer for the earliest of the three. Every verified piece pushes it back, so on a running download it never goes off.

### Pages are pushed to only while one is open

Every push makes the web app fetch the whole page, and the plugin was pushing every second to pages nobody had open.

- **A page being fetched is what says somebody is looking.**
- **A push nobody answers within fifteen seconds** means the tab was closed, and pushing stops.
- **Only a real change is pushed.** The first beat after a page opens is compared with what the page was drawn with, so a stale speed is put right straight away and nothing else is sent.

### The right question, to the right site

- **The sources are PreDB, srrDB and SceneSource**, plus the new PreDB.net. Every one of them is asked about every missing episode on every run: with your resolution, then without it. What the name pool already held only adds to that. It used to stand in for it, so an episode with one refused name in the pool was never asked about again.
- **A source's name goes to every indexer letter for letter**, dots and dash included: `Dark.Matter.2024.S02E03.1080p.WEB.H264-CAKES`.
  - With no rows, the same name is asked without its punctuation.
  - Only then does a site go down the ladder: the episode with and without the resolution, then the season with and without.
  - Each indexer climbs on its own and stops where it answers.
  - The bare show title is never asked. Every name used to go out as loose words.
- **EZTV is an indexer**, not a source. It had put more than three thousand file names into the name pool as if they were releases; those are gone. **EZTV's API ships switched off**, because it answers every question with the same hundred newest torrents. The EZTV site, which does search, stays on.
- **TorrentBay leads for television and Nyaa for anime.** TorrentBay indexes every other site. Where copies are level, its copy is taken and its magnet is the one a torrent is built on. Every other indexer is still asked, and every tracker any of them knew still travels.

### Two indexers had answered nothing for ten days

1337x and EZTV sit behind Cloudflare, and the solver threw away the very page it had been waiting for. A marker it counted as "still challenged" is also on an ordinary page for a session that has just solved one. A cold start now clears all fourteen sites where it cleared twelve.

### Every tracker reaches the client

No indexer's listing carries a magnet, and a magnet was built from the info hash alone, with no trackers at all.

Now every indexer that has the torrent is asked for its own magnet or torrent, and the client gets the trackers of all of them together: seventy on a Dark Matter episode that would have had none. Nothing unannounceable is passed on, and nothing of your own private trackers.

### Take what is found

- **One release under two hashes: both start, and the first to finish is kept.** Each copy downloads into a folder of its own. The other copy is stopped and its files deleted; it is not refused, and its episode is not put back to missing. Nothing taken from a public swarm is ever uploaded or seeded.
- **No seeder minimum.** An episode taken the moment it airs has nobody serving it yet, and refusing it for that refused the exact case worth downloading for. The count still ranks copies; it never refuses one. A copy that never starts is ended by the stall limit.
- **A season pack is an ordinary copy.** There is no gap count to clear and no switch to refuse packs.
- **No search-attempt limit.** It never held: an episode marked unavailable was missing again at the next refresh while its count kept climbing. Every gap is searched on every run.
- **A delivered torrent taken again is delivered again**, from the beginning. It used to be stopped as nobody's, because its earlier grab was done.

### A found episode downloads at once

The sources used to be asked about every episode before any was searched, so the first download waited on the last episode's name.

Now it is one episode at a time. As soon as an episode or a season pack is found, it goes to the client, merged and with every tracker, and the run carries on.

### Stop is a stop, and a run starts from the top

Stop ends the whole run: nothing it had going stays on the page, and Chrome is closed. A stopped run used to skip closing the browser. Downloads keep going.

Every run starts at the top of the queue, so Run after Stop no longer carries on where the stopped run had got to.

### Chrome runs only while a challenge needs it

When a run starts, every site that really challenges is solved at once in one browser, the cookies are kept, and the browser closes. A challenge in the middle of a run opens the browser, is solved, and it closes again.

The browser was also asked for its second job before it was listening, which failed every run's second request.

### The Settings and Sources pages, rebuilt

**Settings**

- **One form and one Save.** A refused value names its field at the top of the page.
- **Show advanced** holds the expert fields and saves nothing itself.
- **A cycle's interval is a choice from a list**, not a cron expression.
- **A speed is a preset** — unlimited, 1, 5, 10 or 25 MB/s — with a box in MB/s for anything else.
- **Seeding is shown only when you have a private tracker.** A public torrent never uploads, so without one those settings decide nothing, and a line says so.
- **The listen port says what is known about it:** open once a peer from outside has reached it, otherwise *not known yet*. The notice telling you to forward the port by hand was drawn from a router refusal, even on a port forwarded since August. It is gone, and so is the port-mapping switch that guarded it. A new install listens on 6881; a configuration that names a port keeps it.
- **Dry run is gone.** It was a testing switch, and the one thing standing between Run and the run happening.

**Sources**

- Every shipped source has its own switch.
- Your own indexers now live on the Sources page, with the API key still write-only.
- YTS and EZTV's API ship switched off.

### The dashboard shows what the plugin is doing

- The status bar says since when a cycle is going, how the last one ended — finished, stopped or failed, kept across a restart — and when the next is due, all as clock times.
- There is a row per stage with its counts: warm-up, names, find, decide, grab, download.
- For every episode being worked on, it shows:
  - which source was asked and what it said;
  - which name was refused and why;
  - every question to every indexer, with the rows it came back with.
- The plugin is on the dashboard and in the user menu. It is no longer beside the libraries.
- Every page answers at the address the web app fetches it from, so the console no longer fills with 404s.

### A quieter log

- No line per tracker that did not answer; the one line per torrent already says how many did.
- Redirects no longer leave "Response body is unavailable for redirect responses" in the server log.
- No "Execution Context was destroyed" from the browser. PuppeteerSharp fails that task internally, and it is now read as soon as it exists: 11 such lines in a warm-up before, 0 after.

### Upgrading

The plugin database migrates itself on the first start, from 007 to 012:
- the last run is kept;
- a second copy gets a folder of its own;
- the attempt counter goes;
- the encode-job column goes;
- the four old cadences become one.

A configuration saved with four cadences loads as one hourly cycle. The server may still hold the four old job registrations. It is answered under their names and starts nothing.

### Not in this release

- **A port that is shut is not said.** Telling *shut* from *not known yet* needs the server to report its reachability (media-server #52).
- **The Settings form has no headings.** The plugin contract has no field for grouping a form, so the groups are reading order only.
- **A server stop can look like failed encodes.** Stopping the server during an encode makes the server report that encode as failed. What the plugin should do with such a report is the next thing looked at.
- **Library loss after a rescan is the server's.** With media-server 0.1.499, a rescan drops the registrations of files under a library folder whose path is empty (media-server #55). An episode the library loses that way is missing to this plugin, and is downloaded again.
