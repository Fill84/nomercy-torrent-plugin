## NoMercy Torrent Downloader — v0.3.17

Two faults on one torrent: a download that could never get its peers back, and a
client that held very nearly the whole file in memory while doing it.

### A torrent that loses its peers finds them again

Every address a run dialled went into a set that nothing ever took it out of.
Exactly one thing cleared that set — a pause followed by a resume — so once the
peers of the first announce were gone, the torrent was finished: each later
announce named the same addresses, every one of them was already in the set, and
no dial was ever made again.

That is a download at nought peers, nought seeds and nought per cent, sitting in
front of a swarm another client on the same machine could see three hundred
seeds in. It had fetched its metadata perfectly well from the peers it then lost.

**The set is a clock.** An address this client is not connected to is offered
again once thirty seconds have passed. A floor there has to be — a peer exchange
arrives about once a minute from every connected peer and names the same
addresses each time, so with none at all one dead address would be dialled on
every message that mentioned it. A peer already being talked to is refused
whatever the clock says.

Three things follow from it:

- **The run keeps an address book.** A pass that did not announce otherwise has
  nowhere to look, and the peers of the last announce are still peers.
- **The announce keeps the tracker's own interval**, whatever the pass around it
  does. Announcing oftener than a tracker asked is how a client gets itself
  banned, and on a private tracker that is an account.
- **No pass dials past fifty peers.** Peer exchange in a large swarm names
  hundreds of addresses within minutes.

A run with nobody left to talk to now comes round every minute rather than
sitting out a half-hour tracker interval with nothing to do.

### One peer is asked for four pieces, not for the torrent

`Pipeline` is four, and its own summary says what that means: how many pieces are
asked of one peer at a time. It was counted per call — and the asking runs on
*every* message a peer sends. So each message claimed up to four more pieces, and
every claim holds a buffer the size of a whole piece until that piece arrives,
fails its hash, or sits unanswered for a minute.

A peer that talks without sending blocks therefore walks the client through the
entire file list. A run of `have` from somebody downloading beside you does it,
and so does a peer that takes the requests and stays quiet. On a 36.1 GB season
pack, whose pieces are several megabytes each, that is very nearly the whole
torrent held in memory: **45 GB resident, with the download showing nought per
cent.**

The count is per peer now. A piece records which peer it was claimed for, that
record is dropped wherever the piece stops being built, and a peer that leaves
stops counting against the one that replaces it. The half-built pieces stay where
they are — the abandon sweep is what gives those back, and it already knows to
throw away what was assembled.

### On the page

The Downloads page says how much of the swarm this client is connected to rather
than its own count alone: **4 of 304** seeds, not 4. Seeds come before peers,
because the number that decides whether a download will finish is how many
machines have all of it.
