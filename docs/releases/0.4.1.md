## NoMercy Torrent Downloader — v0.4.1

A hotfix for one fault with three faces: the server hanging for an hour and a half on
7 September, the server stalling for a minute after a restart, and the web client connecting and
dropping a few times a minute. All three were the client's lock being held while the disk was read,
and every page and every tick queuing behind it — one thread per second until the server had none
left to answer with.

### What changed

- **Adding a torrent no longer reads the disk under the client's lock.** The announce loop leaves
  the lock before it opens the session, so a torrent with gigabytes already on disk is hashed on
  its own thread while every page still answers.
- **Asking whether a torrent holds anything worth downloading no longer opens its session.** The
  run decides that when it opens, and the status pass reads the decision.
- **A peer that dials in while the session is opening no longer deadlocks the run.** It was waited
  for as an event from inside the lock, by a pass that needed the same lock to finish. With a
  forwarded port and a swarm that remembers this client, that is what a restart with a stale
  resume file walked into. The wait is a task now, held by nothing.
- **The page heartbeat drops a tick that finds the last one still out**, looks on its own thread,
  and says once in the log when the client has not answered for thirty seconds — and once when it
  does again. A plugin that has stopped now looks stopped instead of taking the server down.

### What was measured

Three hours on the owner's server with the plugin enabled, a search cycle, eight feed ticks, a
real download and forty-eight connected peers: the server answered every request in under 18 ms.
The fault only shows when a session opens with peers arriving, which is restarts and re-adds.

### Not fixed here

- The magnet field on the Downloads page draws two borders when focused and is not emptied after
  a successful add.
- Everything under *Not fixed here* in 0.4.0.
