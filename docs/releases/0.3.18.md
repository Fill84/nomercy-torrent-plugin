## NoMercy Torrent Downloader — v0.3.18

Every peer in the swarm is now downloaded from, a torrent added by hand reaches
the library, and no piece is held in memory while it is put together.

### Every peer joins the download, not only the one that described it

This is the question 0.3.17 left open: why a season pack fetched its metadata at
05:15 and was at nought peers by 05:29, with hundreds of seeds in the same swarm
that another client could see. Redialling was only half of it. The other half is
that the peers found were never used at all.

The metadata fetch loops while the torrent is unknown, and each turn of that loop
waits on the peer saying something. **A seed says nothing.** It has every piece,
so it sends no `have`; it will not unchoke a client that never said it was
interested; and this client cannot say so until it is in the session. A keep-alive
does not wake the loop either, because the connection swallows those by design.

So the peer that happened to deliver the last block of the metadata exited that
loop and joined the session, and every other peer sat in the read for the rest of
the run — connected, counted on the page, asked for nothing — until the far end
dropped it for being idle. One peer downloading out of however many were found,
and nought when that one went.

The loop now waits on the metadata as well as on the peer. When the metadata wins,
the read already under way is handed to the session rather than abandoned: two
reads on one connection take each other's bytes, and cancelling a read that has
already taken some loses the frame it was in the middle of.

**A peer that does not speak `ut_metadata` is kept too.** It was dropped on the
spot — there is no session to hand it to while the torrent is unknown, so the
conversation ended and the connection with it — which threw away a peer holding
every piece of the file for not being able to describe it.

### A torrent added by hand reaches the library

`AddTorrent` records its grab covering no episode, and deliberately so: claiming
one nobody chose would put that episode back to missing if the download failed.
The comment beside it said such a torrent "answers for whatever it turns out to
hold", and nothing ever worked out what that was. Staging is handed the episodes,
and it chooses nothing when there are none — so a magnet pasted in downloaded in
full and stopped there. A 36 GB season pack sat complete in the download folder
with nothing in the plugin able to move it, and every single episode added the
same way did the same.

The episodes are read out of the torrent's own file names now — never the
torrent's name, never the order the files are listed in — and matched against the
shows the server offers. A file may answer for more than one episode, and a pack
may ship a repack beside the original, so a double episode yields both and the
same episode twice yields one. They are written to the grab rather than only used
for the tick, because every step after staging reads them back: the ownership
check, the file that goes missing, the episode marked arrived, and the torrent
finally cleared.

Nothing is guessed. A video naming a show the owner does not have, or naming no
episode at all, leaves the torrent where the owner put it, and the journal says
why. A grab from the search chain keeps the episode the chain chose.

### No piece is held in memory

A piece was put together in a buffer its whole length and written only once its
hash matched. Every piece being built therefore cost a buffer the size of a piece,
and the number being built is four per peer across fifty peers — two hundred of
them. On a pack whose pieces are megabytes each that is well over a gigabyte of
blocks sitting in memory waiting for their neighbours.

The block is written where it belongs the moment it arrives, and the piece is
hashed by reading it back. What is held instead is which blocks have arrived, at
one bit each.

Unverified bytes now touch the file, which is worth saying out loud because the
opposite was written down as a promise. Nothing reads them as if they were had:
a request for a piece the verified bitfield does not carry is refused, and the
bitfield is only set once the hash matches. A piece that fails is fetched again
from somebody else, over the top of it.

### Proved against the owner's own pack

The pack path was built and never run against anything a scene group actually
publishes. The nine file names are a fixture now, the two text files a release
ships with included. The episode titles are the part that matters:
`Are.You.Happy.in.Your.Life` and `In.the.Fires.of.Dead.Stars` are words where a
parser expects tags, and a pack whose episode four is filed as episode one is
worse than one that stages nothing.

The pipeline depth is asserted exactly rather than at most. Fewer than four is the
regression that would go unnoticed — a cap that slipped to one piece holds no
memory either, and quietly asks a peer for sixteen kibibytes at a time on a link
that could carry a hundred times that.
