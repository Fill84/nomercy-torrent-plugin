## NoMercy Torrent Downloader — v0.4.0

The version where the encode path stops reaching into the media server by name,
and the first one watched end to end on a real server: a forty-five gigabyte
season pack went from a pasted magnet to eight episodes in the library with
nobody pressing anything.

Everything below was found by running it, not by reading it.

### It asks the server for an encode instead of naming its types

0.3.4 reached into the media server and called its classes by name — five
hundred and eighty-eight lines of it — so every server release could break the
plugin silently. `IPluginEncoder` and `PluginLibraryEpisode.Id` do the same work
over the contract, and a server too old to offer them is told so once, in the
log and on the History page, rather than guessed at. It needs contract `0.1.479`
or newer.

One piece of reflection is left and it is deliberate: adding a show the owner
does not have. The contract offers no way to ask a provider about a show or to
queue one of the server's own jobs, and without it a pack for an unknown show
cannot be placed at all. All three types are named at startup, so a server
missing one says so an hour before it matters.

### A pack for a show you do not have

Paste a season pack for something that is in no library and it now: reads its own
file names, finds no show of yours that matches, looks the show up, asks the
server to import it with the same call the dashboard's *Add content* makes, and
on the tick after that import lands takes it on like any other grab — staged in
episode order, one encode per episode, each under its own id.

**Handing files to the encoder without an id does not add a show.** The media
server resolves the id against `Movies.Id` or `Episodes.Id` and nothing else, so
no id matches no row, the job returns having done no work, and the queue records
it finished. On 31 August that was nine files, nine jobs finished inside two
minutes, and nothing written to the library.

### A private torrent trades no peers

**Fix this before anything else if you use a private tracker.** Peer exchange has
a guard for BEP 27 — a private torrent looks for peers on its own tracker and
nowhere else — and both places that actually *receive* an exchange bypassed it.
The outgoing half was refused and the incoming half was taken and dialled. A
private tracker that catches that closes the account, and the ratio goes with it.

Peer exchange also had no limit on what it would read. An address is six bytes
and a peer message may be a mebibyte, so one message could name a hundred and
seventy thousand addresses, every one of them written into a book that was never
emptied. It reads the same fifty it sends now, and the book is bounded.

### Downloads that finish, and disks that do not fill

- A fresh torrent no longer hashes its own empty files before asking anybody for
  a byte. Files were created at full length and then verified, so a forty-five
  gigabyte torrent read forty-five gigabytes of sparse nothing first.
- A torrent keeps the trackers it learned across a restart, and gets them again
  when it is handed back to the client. A magnet off an indexer carries none, so
  such a torrent used to come back with nobody to announce to — one seed and four
  kilobytes a second where the swarm had fifty-two.
- A download that is over leaves nothing behind, and a torrent the client is no
  longer holding still has its files deleted.
- A torrent that will not fit is stopped when its size is known, whoever added
  it. The same disk holds the library and the database.
- A release with no video file in it is refused **for ever** rather than every
  six hours. The flag saying so was set and never passed on.

### Pages that say what is happening

- The swarm columns count two populations: seeds have all of it, peers are
  leechers. Neither is the other subtracted from a total.
- Nought per cent is not nothing arriving. Where bytes are in but no piece has
  completed, the page says how much has arrived.
- How long is left, and a dash where that cannot be known.
- How many peers are choking us, and how many hold anything still wanted — the
  number that says whether a stalled torrent is the swarm's doing or the
  client's.
- The page updates when something changes, carries only what changed, and stays
  quiet when nothing has. It used to stop updating the moment a download stalled,
  which is when it is being watched hardest.
- A port that could not be mapped is not a port that is shut. UPnP failing says
  the router will not open it *by itself*, and nothing about whether it is open.

### Settings that do something

The four cadence fields were checked against a cron parser and then ignored: the
server was handed `* * * * *` whatever was saved. A save that succeeds with a
warning now says the warning — two folders on different volumes make every
completion a full-file copy, which is worth knowing before the first one.

### Not fixed here

- **South Park's `1%` episode, and anything like it.** An encode is registered
  against whatever its filename parses to rather than the episode it was
  dispatched for. That is media-server
  [#38](https://github.com/NoMercy-Entertainment/nomercy-media-server/issues/38),
  fixed on `dev` and not yet in a release. Until it ships, an episode whose title
  contains digits can land under season 0.
- **Anime has not been proved end to end**, for want of an anime library to prove
  it against.
